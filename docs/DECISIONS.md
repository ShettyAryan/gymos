# Implementation decisions

Choices made where `PRD.md` / `TRD.md` left details open. None of them changes product scope.
Each one can be reversed.

| ID | Decision | Why | Where |
|---|---|---|---|
| D-01 | **Routes live in `src/app/`**, not top-level `app/`. | This is the Expo SDK 57 convention, and the TRD allows following Expo conventions. Domain, persistence, remote services and UI stay separated. | `src/app`, `src/domain`, `src/data`, `src/features` |
| D-02 | **The database sits behind a small `SqlDb` interface.** The app uses expo-sqlite. Tests use better-sqlite3 running the same SQL. | Migrations, transactions and outbox atomicity get tested against real SQLite, not mocks. | `src/data/local/db.ts`, `expoDb.ts`, `tests/helpers/nodeDb.ts` |
| D-03 | **SQLite foreign keys are not enabled.** Repositories enforce integrity, and rows are tombstoned rather than deleted. | expo-sqlite's exclusive transactions open a separate connection, so the pragma would apply inconsistently. Soft deletes and sync restore order also don't fit cascading FKs. | `expoDb.ts` |
| D-04 | **All writes and transactions are serialized** through one in-process lock on a single connection. Reads stay concurrent (WAL mode), and `busy_timeout` is set. | A background sync can then never make a set write fail with "database is locked". The test adapter throws if code writes through the root handle inside a transaction, which would deadlock in the app. | `expoDb.ts`, `nodeDb.ts` |
| D-05 | **Cloud storage is one versioned table, `sync_record`.** Each row is `(user_id, entity_type, entity_id, version, payload jsonb)`, protected by RLS, and written through an idempotent `sync_push` RPC. | The device is the source of truth and the cloud is a backup with version checks. One generic table keeps RLS, idempotency and conflict detection in a single tested place. A partial unique index enforces award idempotency keys server-side. A move to typed server tables is possible later if server-side querying is ever needed. | `supabase/migrations/…_init.sql` |
| D-06 | **Conflicts are detected per record using versions.** Each local edit bumps `version`. The server accepts only newer versions. Anything else becomes a visible conflict that the user resolves (keep this device's version or use the cloud's). | This meets "never silently overwrite" for the single-device v1.0 assumption. | `src/data/remote/sync/engine.ts` |
| D-07 | **The programme working copy is separate from immutable approved snapshots** (`programme_version.snapshot`). Workouts always use the active snapshot. Edits set `has_unapproved_changes` until re-approved. | Approval is always explicit, and history is never rewritten. | `repositories/programmes.ts` |
| D-08 | **The schedule is a weekly weekday pattern** for each approved version. A version takes effect on its local approval date, and user-approved reschedules move a single occurrence. | This is the simplest model that supports rest days, streaks, reschedules and changing programmes over time. Rotations not tied to weekdays can be added later. | `domain/rules/schedule.ts` |
| D-09 | **Missed sessions are derived.** A past planned occurrence with no record shows as "Not logged" and breaks the streak. The user can confirm it as missed, reschedule it, or skip with a reason. Illness, travel and life events are excused and neutral. | Missed days don't need a background job, and the user is never punished for legitimate reasons. | `schedule.ts`, `attendance.ts` |
| D-10 | **Streaks count planned sessions attended.** Completed, adapted and partial sessions extend it. Rest days, reschedules, excused skips and habit actions are neutral. | Rewards consistency against the plan rather than daily exercise (FR-08/FR-10). | `schedule.ts` |
| D-11 | **Off-schedule sessions are "extra".** Starting a programme day on a day it isn't scheduled is recorded as extra attendance. Freeform sessions with logged sets count as `completed_as_planned`, since there was no plan to deviate from. | Never credits a scheduled occurrence that didn't happen. | `workouts.ts` |
| D-12 | **Completion status comes from logged working sets.** Any substitution or deferral, or an Adaptive Day session, means `completed_adapted` at best. Any unmet target means `partially_completed`. | Honest labelling (FR-04, FR-06, TRD §6). | `domain/rules/sessionState.ts` |
| D-13 | **Adaptive Day dispositions:** `deferred` means "not today, still in the plan" (time or equipment). `removed` means it conflicts with the user's avoid list and has no alternative. Low energy removes one set, never below 2. Rest periods are never shortened. | Deterministic, explainable rules. Deferred work is never forced into the next day. | `domain/rules/adaptiveDay.ts` |
| D-14 | **XP is flat per event,** with one PR bonus per session (not per PR). Streak milestones are keyed by the date the streak run started. Habit actions earn 5 XP at most once per day. | No reward for volume, nothing to farm, and replays are idempotent. | `domain/rules/xp.ts` |
| D-15 | **Charts use a small in-house SVG component** built on react-native-svg, behind a single component. | Avoids a heavy Skia dependency and keeps the chart library replaceable, as the TRD asks. | `src/components/charts/LineChart.tsx` |
| D-16 | **Forms use controlled state plus Zod/domain validation** instead of React Hook Form. | The forms are small, and this is one fewer dependency. The TRD allows "or equivalent". | `features/onboarding/profileDraft.ts`, `domain/validation/*` |
| D-17 | **AI requests are minimal and use strict schemas.** The Edge Function rejects unknown fields (e.g. `photos`). The client strips identifiers. AI programme drafts are built outline-first, then one request per day, and validated against the user's own exercise catalogue. | Privacy, the free per-minute token budget, and treating AI output as untrusted. | `supabase/functions/_shared/*`, `src/features/coach/*` |
| D-18 | **Malformed AI output does not trigger a fallback** to the next model. Only 429, 5xx, timeouts and unavailable models do (TRD §12). | Avoids spending other models' shared quota on a request problem. | `aiCore.ts` |
| D-19 | **The AI client has a Mock AI mode** that runs on the device, is clearly labelled, and is opt-in. | Lets every AI flow be developed and tested with no credentials, as the TRD's no-credentials mode requires. | `features/coach/mockAi.ts` |
| D-20 | **Photo upload state lives only on the device.** `local_uri`, `upload_status` and `upload_error` are never synced. Restored photos are downloaded on demand through short-lived signed URLs into private storage. | Device paths are meaningless elsewhere, no URL is ever stored, and the bucket stays private. | `entities.ts`, `photoQueue.ts` |
| D-21 | **The rest timer is transient UI state** (Zustand, based on an absolute end time). It does not survive a full process kill. | Workout data is fully persisted; the rest countdown is not workout data. | `src/state/restTimer.ts` |
| D-22 | **The Supabase schema is tested with PGlite** (WASM Postgres, dev-only) plus small stand-ins for Supabase's `auth` and `storage` schemas, run under `node:test`. | Gives real evidence for RLS isolation and `sync_push` idempotency without Docker or a live project. | `tests/sql/supabaseSchema.test.mjs` |
| D-23 | **The project targets Expo SDK 54**, matching the Expo Go 54.0.8 client. It was scaffolded on SDK 57, then downgraded with `expo install --fix`. `expo-status-bar` and `expo-sharing` were removed from `app.json` plugins because they have no config plugin in SDK 54. Android edge-to-edge and the new architecture are enabled (SDK 54 defaults). `expo-notifications` loads lazily, so Expo Go never loads it unless reminders are turned on. | The user's device runs Expo Go 54, so the app must work in Expo Go without a development build. | `package.json`, `app.json`, `features/settings/reminders.ts` |
| D-24 | **"Training instrument" design system.** Near-black canvas and warm off-white ink, with one signal-orange accent used only for live state (active session, timers, progress, PRs). Primary actions use ink. Corners are crisp (4–10px), labels are uppercase micro-labels, and numbers are large and tabular. Lists are hairline-separated with no decorative icons; icons remain only on icon-only buttons. The tab bar is text-only with an accent dot. Status is a dot plus a word. One 20px gutter applies to every screen. Layout primitives (`List`, `Split`, `MetricRow`, `PeriodNav`, `SearchField`, `Button inline/grow`) replace ad-hoc margins and percentage widths. | Requested: a minimal, non-generic UI with properly aligned cards and components. Alignment is now structural (shared gutter, fixed label and date columns, equal-width splits, padded grids) rather than per-screen tweaks. | `src/theme/tokens.ts`, `src/components/*` |
| D-25 | **Typography: Poppins + DM Mono. Motion: built-in `Animated`/`LayoutAnimation` plus `expo-haptics`.**<br>**Fonts:** Poppins (400/500/600/700) for words, DM Mono (400/500) for micro-labels, numbers and timers. Only these six files are bundled. `Text` maps `fontWeight` to the matching file, because Android ignores weight on custom fonts. The splash screen stays up until fonts load; a font failure never blocks the app.<br>**Motion:** sections reveal with a short stagger; buttons, cards and chips scale under the finger; segmented controls have a sliding indicator; metrics count up; progress bars fill smoothly; charts draw on; live state breathes; new sets slide in with a check that pops. Animation is skipped entirely when the OS "Reduce motion" setting is on.<br>**Haptics:** fire only after data is saved and never block logging. | Requested: Poppins with a complementary font, plus interactive and animated elements while staying minimal. Built-in APIs need no extra native setup in Expo Go 54 and keep tests simple. | `src/theme/fonts.ts`, `src/components/motion.tsx`, `src/state/motion.ts`, `src/utils/haptics.ts` |
| D-26 | **Mobile layout fixes.**<br>**App-drawn stack header (`NavHeader`)** replaces the native header. On Android edge-to-edge (SDK 54) the native header drew its title under the status bar and left a gap below it. The app header pads by the safe-area inset and keeps the title truly centred.<br>**Native date picker** (`@react-native-community/datetimepicker`, included in Expo Go) replaces typed YYYY-MM-DD input.<br>**Milestone kinds now mean something:** Weight takes a target and shows the latest weigh-in; Sessions takes a goal and shows live progress; Photo explains the reminder and links to Photos.<br>**Readable controls:** disabled buttons stay visible, and secondary buttons have a lighter fill.<br>**Keyboard handling:** iOS lifts content with `KeyboardAvoidingView`; Android resizes the window. Segmented labels scale down instead of truncating. | User report: the header overlapped the status bar, choosing a milestone type did nothing visible, and the layout did not fit mobile properly. | `src/components/NavHeader.tsx`, `DateField.tsx`, `src/app/campaign.tsx`, `Button.tsx`, `layout.tsx`, `app.json` |
| D-27 | **Logger, streak, calendar and insights additions** (supersedes D-10, and the native date picker in D-26).<br>**Drop sets:** `workout_set.set_kind` is `normal` or `drop`. Drop sets add volume and count in weekly sets, but never toward target sets, PRs, progression or "last time". A set can't be both a warm-up and a drop set.<br>**Supersets:** a shared `superset_group` id on `workout_exercise` and `programme_exercise`. Programme supersets are copied into the approved snapshot and the session. The rest timer starts only after the last exercise in a group.<br>**Finish exercise:** `workout_exercise.finished_at` is a UI marker that can be reopened. It never changes completion status, which still comes from logged sets (D-12).<br>**Undo substitution:** allowed only while the substitute has no logged sets.<br>**Exercise menus:** an in-app action sheet with Cancel replaces `Alert`, because Android shows at most three alert buttons.<br>**Streak = consecutive training days:** a completed planned session or any freeform/extra session extends it; rest and neutral outcomes leave it unchanged; only a day with a missed planned session and no training resets it.<br>**One calendar:** `MonthCalendar` (Monday-first) is used for attendance and every date field, so iOS and Android look the same.<br>**Library v2:** 148 seeded exercises; reseeding keeps custom exercises.<br>**Insights (`insights-v1`):** weekly sets per muscle (primary 1, secondary ½) compared with a goal range (hypertrophy 10–20, strength 6–15, general 6–14); push/pull and quad/hamstring balance; e1RM trends and plateaus; the next load comes from the existing progression rules.<br>**Charts:** weekly sessions/sets/volume bars, e1RM per lift, and body weight. | Requested by the user: cancel in exercise menus, drop sets and supersets, freeform sessions in the streak, a finish-exercise button, a consistent calendar, more exercises, over/undertraining guidance with next-load advice, and graph-based progress. Migration 2 is additive, so existing logs survive app updates. | `migrations/002_sets_supersets.ts`, `workouts.ts`, `supersets.ts`, `schedule.ts`, `MonthCalendar.tsx`, `Sheet.tsx`, `domain/rules/insights.ts`, `app/insights.tsx`, `features/progress/ProgressCharts.tsx` |
